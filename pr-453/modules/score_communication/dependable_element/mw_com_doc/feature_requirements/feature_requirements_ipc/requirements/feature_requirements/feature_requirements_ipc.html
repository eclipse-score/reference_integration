Feature Requirements#

Communication.FEAT_SupportForTimeBasedArchitecture#

The communication framework shall provide API to support a time-based architecture.

Communication.FEAT_SupportForDataDrivenArchitecture#

The communication framework shall provide API to support a data-driven architecture.

Communication.FEAT_SupportForRequestDrivenArchitecture#

The communication framework shall provide API to support a request-driven architecture.

Communication.FEAT_CommunicationInterfaces#

The communication framework shall support communication interfaces composed of any number of the following elements: Events, Methods, Fields, Signals.

Communication.FEAT_EventTypeStructure#

An event-type shall be a named element of a communication interface with an associated data type.

Communication.FEAT_EventAccess#

An event-type shall allow its producer to assign a value and its consumers to either subscribe to value-changed events or poll unseen, cached events.

Communication.FEAT_MethodStructure#

A method shall be defined by a name, a specified application routine with a given set of parameters, and a return type.

Communication.FEAT_MethodInvocation#

When a communication partner calls a method with the required parameters, the method shall invoke its application routine with those parameters, return the result to the caller, and support both synchronous and asynchronous invocation.

Communication.FEAT_FieldTypeStructure#

A field shall be defined by a name, a data type, and dedicated getter and setter methods.

Communication.FEAT_FieldAccess#

A field shall allow its producer to assign a value, and shall allow its consumers to subscribe to value-changed notifications, poll unseen cached values, or retrieve and update the value via its getter and setter methods.

Communication.FEAT_SignalStructure#

A signal shall be a named element of a communication interface that does not transport data.

Communication.FEAT_SignalAccess#

A signal is sent by a service-provider, and it shall be supported, that a service-consumer can wait for its reception and also check/poll if the signal was received or subscribe to update notifications.

Communication.FEAT_ProducerConsumerPattern#

Communication shall be cached based on the producer-consumer pattern.

Communication.FEAT_ServiceInstance#

The communication framework shall support offering multiple service instances for the same interface.

Communication.FEAT_ServiceInstanceNames#

A service instance shall be offered and discoverable under one unique name.

Communication.FEAT_ServiceLocationTransparency#

The interface to access service instances shall be agnostic to the binding used to communicate with the service.

Communication.FEAT_StatelessCommunication#

The communication framework shall support stateless communication.

Communication.FEAT_ServiceInstanceGranularity#

The communication framework shall support multiple service instances per software architecture element.

Communication.FEAT_ServiceDiscovery#

The communication framework shall provide service discovery that considers version compatibility to find available services during runtime.

Communication.FEAT_SafeCommunication#

The communication framework shall support safe communication involving communication partners on the same or multiple criticality levels.

Communication.FEAT_DataCorruption#

Consumers with lower criticality shall not be able to corrupt data consumed by partners with higher criticality.

Communication.FEAT_DataReordering#

Consumers with lower criticality shall not be able to modify the order of data consumed by partners with higher criticality.

Communication.FEAT_DataRepetition#

Consumers with lower criticality shall not be able to duplicate data consumed by other communication partners with higher criticality.

Communication.FEAT_DataLoss#

Consumers with lower criticality shall not be able to drop data before it is consumed by partners with higher criticality.

Communication.FEAT_ZeroCopy#

The communication framework shall enable Zero-Copy communication without copying to-be-transferred data.

Communication.FEAT_SupportForMultipleProgrammingLanguages#

The communication framework shall provide a public API for each supported programming language of S-CORE.

Communication.FEAT_SupportForProgrammingLanguageIdioms#

Each public API shall support the idioms of the programming language it is written in.

Communication.FEAT_UseProgrammingLanguageInfrastructure#

Each public API shall use core infrastructure of its programming language and its accompanying standard libraries.

Communication.FEAT_FullyMockablePublicAPI#

The public API shall be fully mockable.

Communication.FEAT_FakeBinding#

The communication framework shall provide a fake binding.

Communication.FEAT_MultiBindingSupport#

The communication framework shall support multiple bindings.

Communication.FEAT_BindingAgnosticPublicAPI#

The public API of the communication framework shall be binding-agnostic.

Communication.FEAT_MultiBindingDeploymentConfiguration#

The association between a service instance and its binding shall be specified in the deployment configuration.

Communication.FEAT_DeploymentConfigurationAtRuntime#

Deployment configuration shall be read from an integrity-checked configuration file at runtime.

Communication.FEAT_SupportForTracing#

The communication framework shall provide infrastructure to enable binding-agnostic, zero-copy, read-only tracing of communication.

Communication.FEAT_AccessControlListPerServiceInstance#

The communication framework shall support an Access Control List per service instance.

Communication.FEAT_AccessControlListForProducer#

The communication framework shall support an Access Control List for the communication partner offering a service instance (producer).

Communication.FEAT_AccessControlListForConsumer#

The communication framework shall support an Access Control List for the communication partner consuming a service instance.

Communication.FEAT_CommunicationASILLevel#

The communication framework shall support safe communication up to ASIL-B.

Communication.FEAT_CommunicationPartnerCrashRecovery#

The communication framework shall support crash recovery and allow a communication partner to rejoin an earlier initialized communication after an application termination.

Communication.FEAT_CommunicationAcrossOSBoundaries#

The communication framework shall support technologies which allow communication across operating system boundaries.

Communication.FEAT_ErrorHandling#

(C++) exceptions shall not be used for error handling. The best way to deal with errors is to try to resolve those component internally. If not possible the caller of the function shall be notified of the error. For (error) returns there is a specific library to be used in S-CORE, it is the Score::Result library which is part of the Base Libraries feature.
