Introduction/Scope#

This manual covers the module Persistency with the feature Persistency, which is realized by the component KVS (persistency::kvs (comp__persistency_kvs)) in a C++ and a Rust implementation.
The module is developed as Out of Context (OoC). This manual defines the requirements for the secure integration and usage of the module.

Assumptions on the Environment#

The platform and its components are developed as Out of Context (OoC) with assumptions on the environment. It is assumed that the platform/components are integrated in a secure system, i.e. qualified POSIX OS. Also the HW related failures are taken into account by the system integrator, if not otherwise stated in the module’s security concept.
The module expects the following OS services to be secure:
- file system access: open, read, write, flush and sync to the storage (fdatasync), rename and remove of files, creation of directories. The C++ implementation uses them via score::filesystem of the baselibs and the C standard library, the Rust implementation via the Rust standard library (std::fs);
- enforcement of the file system access rights (user, group and permission bits) for these calls;
- process isolation, i.e. the memory of the application using Persistency can not be read or modified by other processes;
- thread synchronization (mutex);
- heap memory allocation.

Assumptions on the User#

As there is no assumption on which specific OS and HW is used, the integration testing of the stakeholder and feature requirements is expected to be performed by the user of the platform OoC. Tests covering all stakeholder and feature requirements performed on a reference platform (tbd link to reference platform specification), reviewed and passed are included in the platform OoC security package.
Additionally the components of the platform may have additional specific assumptions how they are used. These are part of every module documentation: Persistency Documentation. Assumptions from components to their users can be fulfilled in two ways:
1. There are assumption which need to be fulfilled by all SW components, e.g. “every user of an IPC mechanism needs to make sure that he provides correct data (e.g. including appropriate security (access) control)” - in this case the AoU is marked as “platform”.
2. There are assumption which can be fulfilled by a security control realized by some other S-CORE platform component and are therefore not relevant for an user who uses the whole platform. But those are relevant if you chose to use the module OoC stand-alone - in this case the AoU is marked as “module”.

Security concept of the OoC#

Persistency is a library which is executed in the process and with the OS user of the calling application. It has no own process, no inter-process communication and no network interface. Its attack surface consists of its API, used by the application, and of the files it stores in and loads from the file system (storage, snapshot and default-values files, see Persistency KVS Feature Arc... (doc__persistency_kvs_architecture)).
Access control: the component does not implement own access controls, but relies on the access rights of the file system (Permission Control (comp_req__kvs__permission_control)). Access and permission errors of the file system are reported to the application (Permission Error Handling (comp_req__kvs__permission_err_hndl)). The separation of the data stores of different applications (Separate data stores (feat_req__persistency__access_control)) is therefore achieved by the system integrator (Storage Access Rights (aou_req__persistency__storage_access_rights), Read-only Default Values (aou_req__persistency__defaults_read_only)).
Integrity: when a storage file is loaded, its Adler-32 checksum is compared with the stored checksum. Corrupted or interrupted storage is detected, reported and not loaded (Corruption Detection on Open (comp_req__kvs__corruption_detect_open), Open Behavior on Missing or... (comp_req__kvs__open_need_kvs_behavior)). Adler-32 is not a cryptographic checksum, i.e. it detects accidental corruption, but not intentional manipulation by an attacker with write access to the storage (No Protection against Inten... (aou_req__persistency__manipulation_protection)).
Availability: flush operations keep the previously persisted consistent data until the new data is completely written (Reset Resistant Write (comp_req__kvs__reset_resistant_write)), previous states are kept as snapshots, whose number is limited (Maximum Number of Snapshots (comp_req__kvs__snapshot_max_num_cfg)). Keys are limited in length and character set (Key Length (comp_req__kvs__key_length), Key Naming (comp_req__kvs__key_naming)). Input of malformed storage files is rejected by the JSON parser and reported as error.
Confidentiality: the component stores the key-value pairs unencrypted. The confidential storage (Confidential storage (feat_req__persistency__confidential_storage)) is not realized by the component, it has to be provided by the storage environment (Confidentiality of Persiste... (aou_req__persistency__confidentiality)).
Tooling: the KVS tool (//score/kvs/rust_kvs_tool:kvs_tool) reads and modifies KVS storage for development and test purposes. It has no special rights and can only access the KVS storage accessible to the OS user running it, which is restricted by Storage Access Rights (aou_req__persistency__storage_access_rights). It is recommended not to deploy the KVS tool in production software images, to keep the attack surface small.
The security analysis of the feature is documented in STRIDE (doc__persistency_stride).

Software Bill of Material (SBOM)#

The SBOM of the module (Module Software Bill of Mat... (wp__sw_module_sbom)) is generated by the Bazel target //:sbom_product in the formats SPDX 2.3 (sbom_product.spdx.json) and CycloneDX 1.6 (sbom_product.cdx.json). It lists the dependencies of the product targets //score/kvs:kvs (C++) and //score/kvs/rust_kvs:rust_kvs (Rust) with version, license and supplier. The SBOM is generated on demand with bazel build //:sbom_product and is not yet part of the release workflow.
Build-time, test and documentation tooling is not part of the product and is listed separately by the Bazel target //:sbom_docs_tests.

Security Weaknesses, Vulnerabilities#

Weaknesses, vulnerabilities (bugs in security relevant SW, detected by testing or by users, which could not be fixed) known before release are documented in the module release notes Persistency Release Note (doc__persistency_release_note).
Open security topics at the time of this manual version:
- Storage File Permissions (comp_req__kvs__storage_file_permissions) (storage files created with permissions 640) is not yet implemented, the storage files are created with the default permissions of the process (umask), see #412. Until then Storage Access Rights (aou_req__persistency__storage_access_rights) has to be fulfilled via the access rights of the KVS working directory.
- Default Storage File Permis... (comp_req__kvs__default_storage_permissions) (default-values file generated by the KVS tool with permissions 440) is not yet implemented, the KVS tool does not yet handle default-values files, see #505. Until then Read-only Default Values (aou_req__persistency__defaults_read_only) has to be fulfilled during deployment.
